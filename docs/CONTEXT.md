# 프로젝트 현재 상태

기준일: 2026-11-24. 새 대화에는 이 파일을 먼저 전달하고 작업에 해당하는 기준 문서·코드만 추가한다.

## 목적과 구조

도매매·오너클랜 상품/변경 이력, 쿠팡 베스트, 네이버 시즌 키워드를 PostgreSQL에 저장하고 공급 점수와 홈 추천을 계산한다. 완료 결과 조회·HTTP API·사용자 기능은 Spring Platform 책임이다. Python 3.12/PostgreSQL16/requests/psycopg/PyYAML을 사용한다.

공통 코드는 `product_data_collector/`, 공급처 코드는 `ownerclan_API/`, `domeggook_API/`, `coupang_API/`, `naver_API/`다. 도매매 동기화는 `workflows/product_sync.py`·`sync_cli.py`; schema 모듈과 기존 migration 식별자는 [DATABASE](DATABASE.md#migration과-백필), 배치는 [README](../README.md#폴더와-문서)를 따른다. 저장된 CLI·migration·잠금·checkpoint 호환 이름은 유지한다.

2026-11-24 승인 후 Docker DB에 점수·운영 migration 네 개와 `runtime_budget_guard`, 최소 권한 계획을 적용했다. 적용 전 백업을 격리 복원했고, 적용 후 기존 업무 데이터 542,173행의 내용 해시와 상세 미완료 184,385건이 동일했다. Spring 전용 로그인 `chozy_spring_budget`으로 실제 JDBC 접속과 예약 함수 실행을 확인했다. 기존 수집기 로그인은 여전히 superuser이며 수집기는 대기 중이다. 공동 예산 정책은 0건이며 외부 호출과 자동화는 대기다. 권한 근거는 [VALIDATION](VALIDATION.md#db-권한-분리-검증)을 따른다.

Compose 기본은 PostgreSQL만 시작한다. 선택형 data-collector도 대기하며 operations는 기본 오프라인 plan, automatic_enabled=false/schedules=[]다. 기존 개발 wrapper는 수집까지만 하고 점수/발행은 연결하지 않는다. 실제 실행/중단·배포는 [RUNBOOK](RUNBOOK.md) 기준이다.

## 오너클랜 수집과 최신 결과

`itemHistories → 이벤트/상세 요청 저장 → 고유 변경 key → itemsByKeys 최대100개 → 요청/반환 key 대조 → 누락만 제한 보완`이다. POST JSON, connect 최대5초/read 최소45초, 누락만1초 뒤1회 보완하며 끝내 누락되면 retry로 남긴다. HTTP200이나 순서로 완료 판단하지 않고 403/429·GraphQL 제한은 중단한다. 구현은 `ownerclan_API/workflows/history_sync.py`, `api/{queries,client}.py`, 공통 `persistence/detail_refresh.py`다.

앞선 약 5,000개 시험은 **진단 controller가 보완 후 미반환에서 나머지 전송을 막아 실제 업무 동작을 변경한 부분 실험**이었다. 따라서 299개에서 멈춘 결과를 실제 수집기의 E2E 실패로 보고한 것은 잘못이다. 업무 worker는 미반환만 재시도 대기열에 남기고 다음 묶음을 계속 수집한다. 잘못된 controller 중단 조건을 제거했고, 격리 회귀에서 `100개 요청→99개 저장→누락1개 보완 실패→다음100개 저장`, 총199개 저장/미완료1개를 확인했다. 이 정정에서는 실제 API를 추가 호출하지 않았다.

당시 API의99/100·보완0/1 응답은 유효한 관측이지만, 약5,000개 전체 시도는 미측정이다. 앞200개만의 약3시간 환산은 **운영 처리시간 판단으로 철회**한다. 별도 기존 스냅샷5,000개 점수+발행7.619초도 오프라인 재생일 뿐이다. 실제 worker와 동일한 수집 지속 조건에서 다시 측정해야 한다. 원시 결과·정정·한계는 [검증 기록](VALIDATION.md#오너클랜-5000개-표본-e2e)에 둔다.

기존03:41 소량 재확인은 인증1+조회3, 10.328초·오류/누락0이었다. 과거 문제 key의 bulk1/item 헤더 응답은 .297/1.250초였다. 직전 교차 시험에서는 같은 bulk query가 정상 반환 뒤 HTTP200의 정확한 빈 배열을 반환했다. 따라서 일시적 정상 응답을 원인 해결·대량 회복으로 해석하지 않는다. 서버/연결 인과와 계정 전체 사용량·제공처 한도는 미확정이다. 수치·과거 분석·원문 hash는 [VALIDATION](VALIDATION.md#오너클랜-api-지연-실측)에 모았다.

최신 고정100개 묶음 비교에서100/50/20개 방식은 각각100개 확보, 10개 방식은 빈 배열1회로90개 확보였다. 단건은 계측 오류로 최초 부분 관측을 제외하고 별도 Session/JWT로 재측정했으나24번째 요청의 HTTP200 GraphQL 제한 오류에서 중단했다(정상22·누락1·제한1). 작은 묶음의 누락 해결은 입증되지 않았고 단건100개 완주·순서 교대 반복·대량 회복은 미검증이다. 제한 후 추가 호출/자동 재개는 하지 않았다. 조건·시간·전체 호출 기록과 계측 오류 한계는 [묶음 비교 실측](VALIDATION.md#묶음-크기-비교-실측)에 둔다.

일일 **고유 변경 약10만 상품**은 과거 관측과 계획 가정이다. 점수 입력은 `변경 ∪ 공급사 영향 ∪ 만료`이고 발행은 **전체 유효 집합**이므로 모두10만이라고 가정하지 않는다. 전체 카탈로그1,500만 성능/저장 용량은 미검증이다.

## 지켜야 할 데이터 의미

- products=최신 상태, product_history=실제 변경 관측, product_events=출처 있는 원본/관측 사건. 관측을 원본 사건으로 만들지 않는다.
- DB commit 확인 뒤 checkpoint 전진. 피드 순회 완료와 상세 반영 완료는 별개다. 늦은 응답·낮은 요청 버전이 최신값을 덮어쓰거나 미반환을 삭제/완료로 처리하면 안 된다.
- NULL·미확인·0, 옵션 추가금·최종 공급가를 구분한다. 피드 순회/최초 적재일은 90일 coverage나 공급사 인증 근거가 아니다.
- 점수 중 같은 소싱처 입력을 보호하고 미완료 발행을 차단하며 이전 완료본을 보존한다. 일반 startup은 기존 DB를 자동 migration하지 않는다.

## 다음 작업 순서

사용자 요청으로 고정100개 묶음 비교를 실행했고 현재는 **GraphQL 제한 오류로 중단**한 상태다. 자동 재개하지 않는다. 재개 전 계정 공동 사용/제공처 한도·reset을 확인해야 하며, 단건100개 완주와 순서 교대 반복은 미완료다. [실측과 한계](VALIDATION.md#묶음-크기-비교-실측)를 따른다.

사용자가 지정한 1번 성능 검증과 3번 운영 전환의 남은 범위는 아래와 같다.

| 작업 | 완료한 범위 | 반드시 남은 작업 |
| --- | --- | --- |
| 1번 성능 | 기존 발행 시간 단위 확인, 10만/50만×6조건×3회 쓰기·인덱스·FK·WAL/I/O 계측, 동일 FK/고유 인덱스의 충돌 처리 비교와 최적화 채택, 1,500만 검증 계획 | 합성 조건 밖 실제 분포·운영 동시 부하 검증, 목표 서버/분포/SLA/보관 기간 확정 후 100만→300만→500만→1,500만 성능·저장 용량 실측. 계획 작성을 실측 완료로 간주하지 않음 |
| 3번 운영 전환 | 운영 백업·격리 복원, migration과 권한 계획 적용, Spring 전용 로그인 실제 JDBC 접속 확인 | 수집기 전용 로그인·DSN 전환, 계정별 공동 예산 등록, Spring 검증 인스턴스 활성화와 실제 예약·조회 확인 |

세부 측정 계획/근거는 [VALIDATION](VALIDATION.md#1500만-규모와-운영-승인-전-남은-조건), 적용 순서/복구는 [RUNBOOK](RUNBOOK.md#운영-전환-준비와-적용-순서)를 따른다. 위 기록은 작업 재개나 운영 변경 승인이 아니다.

1. 비용 분리/충돌 처리 최적화의 합성 결과를 운영 SLA로 확장하지 않는다. 목표 서버·실제 분포·SLA·배치 보관 기간을 확정해 100만→300만→500만→1,500만으로 검증한다. API 지속 처리/회복 시험은 별도 재개 범위가 정해진 뒤 수행한다. 강제 planner/work_mem/CTE 대안은 채택하지 않았다.
2. 병행: 오너클랜 제공처 trace/한도 확인, 도매매 Private 승인·성공 계약 실측. 실제 호출은 그때 승인한 범위·중단 조건을 따른다.
3. 수집기 runtime 로그인과 DSN을 전환하고, 승인된 계정별 공동 예산을 등록한 뒤 Spring 검증 인스턴스에서 예약 흐름을 확인한다.
4. 승인된 schema/계정예산/상태 mount/감시 아래 수집 재개, 당시 pending 수량 재확인·상세 해소. 미완료면 점수/발행 금지.
5. 실제 initial→완료 후 새 job incremental, Spring 실제 역할·예약/조회/알림·중단/재개 검증 후 별도 자동화 승인.
